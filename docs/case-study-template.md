# Editorial case-study template

This is an opt-in page family within the portfolio design system. It prepares future studies; it does not migrate the existing project pages. The unlisted reference is at `/design-system/case-study.html`.

## Ownership and stylesheet order

- General pages keep their current shared styles and starter.
- Existing studies keep `case-study.css`, their `cs-*` classes, and their project exceptions.
- New editorial studies start from `templates/case-study.html.template`. Use the `case-study-editorial` body class and `cse-*` components. Do not mix these with `case-study-page`, `cs-*` layout classes, or `case-study.css`.

Load Webflow CSS → design tokens → shared site chrome → case-study editorial CSS. Load the shared font, favicon, and chrome script as in the starter, then the editorial script. No framework or build-time include is required. Header/footer markup is duplicated in this static site: update both starters and the reference when changing shared chrome.

`css/design-tokens.css` owns shared foundations. `css/case-study-editorial.css` owns scoped `--cse-*` roles and editorial components. `js/case-study-editorial.js` enhances opted-in section navigation and supporting-content disclosures. Reference copy demonstrates components; it is not a project narrative to copy into new studies.

## Layout contract

The main layout contains a left section-navigation rail and an article. Each article section reserves a right track, even without a note. Body text is centred in the viewport, up to the shared 760px reading width. Figures, captions, and comparisons default to the same centred 760px column and horizontal margins as text. A deliberate `cse-wide` modifier lets evidence use the central track up to 1200px. Actual media width is smaller whenever the viewport must accommodate rails; it never overlaps them.

| Width | Navigation | Right notes | Gutters and rails |
| --- | --- | --- | --- |
| ≥1440px | Sticky markers + current name; full list on hover/focus | Beside their related fragment; scroll normally | 32px outer gutters/gaps; equal 200px rails |
| 1024–1439px | Same reading navigator; full list on hover/focus | Beside their related fragment; scroll normally | 24px gutters/gaps; equal 160px rails |
| 768–1023px | Section row attached to the website header | Opt-in support disclosures in the reading flow | 24px gutters; no rails |
| <768px | Same section bar | Opt-in support disclosures in the reading flow; comparisons and facts stack | 20px gutters; no rails |

The enhanced navigator appears when the first story heading reaches the reading position below the header, and hides again when returning to the opening or leaving the article. Mark the opening with `data-cse-opening`; it must be one of the linked sections. Hidden navigation is inert and excluded from the keyboard order. Returning to the opening hides the control even when it held keyboard focus; focus moves to the visible heading. Its desktop position is fixed to the reserved rail, measured from the main layout, so appearance and expansion never shift the article.

On desktop, inactive sections are short muted lines and the current section shows its name in the accent colour. Hover anywhere over the control or focus any link to reveal every label in a surface panel. The panel can overlap the reading area temporarily; it never resizes the content. At intermediate widths, 160px symmetric rails provide room for the current name. Current names wrap fully. Use concise navigation labels rather than repeating long section headings. Touch users at desktop widths tap once to expand and again to select. Clicking outside resets that expansion.

On smaller screens, a 44px row docks flush to the bottom of the website header, matching its width and bottom corners. It shows the current section, a chevron, and a quiet reading-progress line. Without JavaScript, “Explore this study” supplies a visible disclosure label. Its native disclosure opens a scrollable surface panel; opening it does not move the article. Enter/Space toggle it, Escape closes it and returns focus to the bar, and selecting a section closes it and moves focus to the destination heading. Clicking outside or moving keyboard focus away closes it. Long lists scroll within the available screen height. The website menu takes priority and temporarily hides the section row.

The script measures the header and subtracts shared HTML scroll padding from the scoped scroll margin, avoiding doubled clearance. Mobile targets also clear the section bar. Link selection uses smooth native scrolling; reduced-motion preferences use an instant jump and suppress reveal transitions. Scrolling updates the current section without moving keyboard focus. Hash links, direct entry, and browser history remain supported.

Without JavaScript, section links remain visible throughout: desktop shows full labels; mobile uses an open disclosure in normal flow, so it cannot cover native anchor targets. The fallback does not depend on hover or scroll detection.

These thresholds apply only to this family. They do not consolidate existing website breakpoints.

## Typography, colour, and deliberate exceptions

Open Sans and 400/600/700 weights inherit shared tokens. Body is 20px/32px, becoming 18px/29px below 768px. Captions/notes use 14px/22px; fact labels use 13px/20px. Editorial titles are `clamp(36px, 5vw, 64px)` at 1.1 line height, section headings `clamp(26px, 3vw, 36px)` at 1.2, supporting headings `clamp(22px, 2.2vw, 28px)` at 1.25. Paragraph/fragment gaps use 24px; section spacing uses 80px, becoming 64px below 1024px.

The smaller heading scale, mobile body role, 200px/160px rails, and anchor clearance are intentional editorial exceptions. Spacing, shape, and existing widths still reuse shared tokens. If a project needs another exception, scope it under its page class and explain it in implementation notes; do not change shared foundations to accommodate one figure.

All portfolio colours inherit semantic `--ds-*` roles through scoped aliases. Headings, result titles, result headlines, and result values use `--ds-text-heading`; narrative text uses `--ds-text`. Narrative paragraphs, lists, and callout prose explicitly use `--cse-text`; do not mute a whole narrative block. Captions, video cues, side notes, and metric labels use `--ds-text-muted`. Links and selected navigation use `--ds-accent-primary`, while the callout rule uses `--ds-accent-evidence`. Change these shared roles rather than adding fixed palette colours to the template. This family uses a plain page background rather than the general site's decorative radial background. It has no separate theme or fixed light/dark palette. Future global theme overrides should change the shared semantic roles; the article, controls, and notes will inherit them. Global light mode, system preference detection, theme switching, and persistence remain future work. Image colours remain project evidence and are not recoloured by theme tokens.

## Component recipes

Keep one h1, logical heading levels, descriptive titles, and truthful evidence. Read the portfolio content guide before authoring copy. Structure the story around the actual work rather than filling a compulsory process sequence.

- **Introduction:** use `cse-section` on the article header, a `cse-title`, a `cse-prose cse-lede` summary, a contribution paragraph, and the required `dl.cse-facts` opening component. This applies both to new studies and explicitly requested editorial rebuilds. Keep facts in the opening, visible outside supporting disclosures; ordinary role/collaboration paragraphs do not replace this component. The starter provides Project, Role, Period, and Collaborators, matching the reference’s pattern. Populate only verified facts and remove individual unknown or inapplicable entries rather than inventing data. Labels and entry count may adapt to the project; four filled fields are not compulsory. If no facts can be verified, resolve the evidence gap before treating the page as ready. Contribution prose should explain responsibilities and decisions without repeating the compact facts.
- **Narrative section:** give `cse-section` a stable unique ID and `aria-labelledby` pointing at its `cse-heading`. Use `cse-subheading` for h3s and `cse-prose` around paragraphs/lists. The heading need not match a formula.
- **Reading figure:** use `figure.cse-figure`, a `cse-media` wrapper or full-size image link, and `figcaption.cse-caption`. Include truthful alt text and intrinsic image width/height; use lazy loading below the fold. Add `cse-wide` only when a wider visual is requested or a documented legibility need warrants it. Agents may recommend this option with a clear reason; it is not the default.
- **Device figure:** inside a normal `cse-figure`, wrap `cse-media` with `div.cse-device` and `div.cse-device-shell`. Choose exactly one modifier: `cse-device--phone` or `cse-device--desktop`. The starter contains optional image and video recipes in a commented block; move the chosen figure into its related narrative section and delete unused recipes. Both frames accept either an image link or a native video in `cse-media`. Keep `figcaption.cse-caption` outside the device. The outer figure and caption stay at the centred text width; the phone itself is centred and capped at 320px. Put an explicitly justified `cse-wide` on the figure if a desktop screen needs more room. Do not wrap evidence that already contains a device frame. Use screenshots without hardware; never stretch, crop, or overlay a notch on evidence to fit an invented aspect ratio.
- **Device video:** swap the image link for `div.cse-media` containing `video controls playsinline preload="none"`, intrinsic width/height, a truthful poster with the same proportions, a typed `source`, and an accessible label. Include a descriptive direct video link in the caption as well as fallback content. Avoid autoplay and looping; the reader controls motion. Supply captions/transcripts where audio conveys meaning, and describe essential visual interactions in the surrounding narrative. Do not treat this template’s silent visual example as sufficient for other recordings.
- **Comparison:** use `cse-comparison` containing complete figures and captions. It stacks below 768px. Explain what is compared; do not imply measured improvement merely by pairing images.
- **Callout:** combine `cse-prose cse-callout`; use a real heading only when the point needs one. Use the open treatment with a slim evidence-accent rule, no filled surface, a body-sized medium-weight heading, and an 8px heading-to-copy gap. Keep essential narrative in the reading flow.
- **Results:** use the optional `#results` section and one flexible `cse-result` block from the starter. Add a `cse-result-title` h3, an optional `cse-result-headline`, and a `cse-results-grid` definition list. Each metric has a semantic `dt` label, a `cse-result-value` value, and optional `cse-result-source` context. The same block supports before/after values or independently reported metrics by changing the labels and copy; no variant classes are needed. Keep units, reporting periods, methods, attribution, limitations, and descriptive source links close to the values. Cards default to the 760px reading column, inherit existing heading/body/caption roles and surface/border/radius tokens, and stack below 768px. Do not infer causation from a business metric or compare different samples without explaining their limits. Remove the section and its navigation link if results are unavailable. Add or remove list entries to match the evidence; never invent numbers to fill columns.
- **Optional short note:** use `cse-pair` with exactly two direct children: the related prose/figure first, then `aside.cse-note.cse-support`. The aside contains `details.cse-support-disclosure` with `open` in source, a descriptive `summary.cse-support-summary`, and `div.cse-support-content`. Give the summary a unique ID and reference it with the aside’s `aria-labelledby`. Use the starter’s `cse-note-title` span and decorative `cse-support-chevron`. It appears beside the fragment at desktop widths (1024px+) and as a compact disclosure immediately after it on smaller screens. Do not use generic labels such as “More” when a topic can be named.
- **Illustrated supporting story:** group all remaining primary fragments of the section in `div.cse-support-main`, the first child of a `cse-pair`; put one support aside second. The group can contain prose, headings, reading figures, or deliberately wide figures. The aside aligns with the start of the group in the wide margin and follows the complete group at the section’s end below 1024px. Keep its images and captions together inside one disclosure. Name it specifically, for example “Illustrated discussion: comparing the options”, and retain “Illustrative dialogue/scenario/summary” identification with the content. Group complete `figure` patterns in `div.cse-support-gallery` when the story contains illustrations. Each illustration is capped at 280px: two appear side by side at 480–1023px, while narrower screens and the desktop margin use one column. Captions stay with each image, intrinsic proportions remain intact, and full-size links retain access to illustration detail. A single illustration stays compact and centred. This deliberate cap prevents optional illustrations from dominating the reading flow. Do not place more primary fragments after this pair if the supporting story should finish the section.
- **Existing margin note:** unmodified `aside.cse-note` keeps the previous visible inline fallback. Only the additional `cse-support` / `cse-support-disclosure` classes opt into the new behaviour; existing studies are not migrated by shared template work.
- **No note:** use prose/figures directly in the section, or remove the aside from its pair. The reserved right track remains. Never add an empty aside just to hold the column open.

Section links are authored ordinary anchors, not inferred from generic heading text. Add one link for each `cse-section` (including overview) in document order; use its exact ID and a concise sentence-case label. Retain the `cse-nav-marker` (aria-hidden) and full `cse-nav-label` spans, plus the starter’s summary accessible name/current-name/chevron/progress markup. Mark the article opening with `data-cse-opening` so future agents do not guess where the main story starts. JavaScript manages `aria-current="location"`; authors should not hardcode several current links. Keep IDs stable after publishing so shared deep links remain valid.

## Creating a future case study

1. Copy the dedicated case-study starter to the intended HTML route. Retain root-relative asset paths for the current site-root deployment; adjust all paths together for any future subdirectory deployment.
2. Replace all `{{...}}` placeholders, escaping text and attribute values as HTML. Set the actual production canonical URL, description, social metadata, and optional preview image. Remove unused optional blocks rather than publishing placeholder text.
3. Retain `dl.cse-facts` inside the opening header and populate its verified entries; check that it has not been replaced with prose or hidden in a disclosure. Add verified project material and adapt the section order. Preserve contribution, outcome qualifiers, and source-backed captions. Never invent metrics, research, quotations, or illustrative evidence.
4. Keep draft noindex metadata until intentionally publishing the page. Only mark a shared navigation destination current when the route actually matches it. Preserve mobile navigation, landmarks, skip link, and footer.
5. Register the new page in the site-consistency route list and `ROUTES` in the editorial audit. Add navigation/sitemap entries only when intentional publishing calls for them. Keep references unlisted and noindex.
6. Run the foundation audit, its guard tests, and publish audit against a local server. Check the real new page on mobile/desktop, keyboard, reduced motion, full-size media links, and immediately around the new breakpoints. Audit registration requires the same section/nav contract as the reference; noindex is required only for the reference route.

## Checks and maintenance

Run `node scripts/design-foundation-audit.mjs`, `node --test scripts/design-foundation-audit.test.mjs`, and `node scripts/publish-audit.mjs` with the preview server running (`SITE_BASE` defaults to `http://127.0.0.1:8080`). The publish audit includes `scripts/editorial-template-audit.mjs` independently of legacy case-study geometry checks. The foundation audit also guards the starter’s opening facts component and its four field placeholders; it does not retroactively require changes to existing project pages. Review each new or explicitly rebuilt study against the facts checklist before completion.

The editorial audit checks missing roles, CSS scoping, section links, image loading, noindex on the reference, reading/media geometry, note placement/removal, responsive boundaries, keyboard focus, opening visibility/inert state, all-label hover/focus reveal, the mobile current-section bar, long lists, sticky anchor clearance, native links without JS, and inheritance from simulated shared semantic overrides. It does not replace checking writing accuracy, image legibility, or project-specific contrast. Update the reference and recipes together when changing a component.

See `docs/case-study-template-verification.md` for actual contrast measurements, baseline comparison results, and verification limitations.

Standalone `cse-caption` paragraphs inside a section use the same centred reading column as narrative text. Captions inside figures stay within their figure. Preserve automatic horizontal margins when adjusting caption spacing.

The results reference uses the existing BetaTrends evaluation. Replace every result placeholder and verify sources before publication; the reference numbers are not defaults for another project.

The unlisted reference result card omits its visible source note to demonstrate the compact presentation. Its example comes from `/projects/creator-delight/#creation-time-result`: 21 min 52 sec before, 11 min 38 sec after, and a reported 47% reduction. This separate evaluation drew on Hotjar and Maze evidence; it is not calculated from the individual Maze task comparisons. Published case studies still need appropriate source and method context, in the card or the surrounding narrative.

## Responsive supporting content

Supporting disclosures default open at 1024px and above, and collapsed below that boundary when JavaScript is available. The reader can still toggle them at any size. Multiple disclosures can remain open together. An inline choice is remembered only in the current page’s memory across resizing; there is no storage or preference setting. Resizing to desktop opens the margin presentation; returning to inline restores the reader’s previous inline choice. If resizing would hide a focused link, focus moves to that disclosure’s summary.

Native Enter/Space activation, visible shared focus rings, and descriptive summaries remain available. Escape closes an open disclosure and returns focus to its summary. Content expands in normal flow with no height animation; only the chevron and hover colour transition use shared motion tokens and reduced-motion rules. With JavaScript disabled, the authored `open` attribute leaves all support visible at first, and native controls still work. In-page hashes to the support aside or content reveal its disclosure when enhanced. Keep one content copy; do not duplicate desktop/mobile text or images.

Choose content before presentation: essential decisions, contribution, research findings, results, sample/method limits, and context needed to interpret a claim stay visible in primary prose. Collapse only supplementary explanation or illustrations. Remove redundancy instead of hiding it behind a control. The reference demonstrates a short source note and a two-image illustrated discussion using the existing verified BetaTrends material; its labels do not imply real transcripts.

The new support treatment is an opt-in template pattern. Adopting it on an existing study requires an explicit migration task. Keep the reference, starter, documentation, and editorial audit aligned when modifying this behaviour.
